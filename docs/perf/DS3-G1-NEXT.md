# DS3 после G1: куда уходит кадр и что дальше

Дата: 21.10.2026. Журнал G1: `logs/ds3/DarkSoulsIII.exe-2026-10-21_12-52-56.txt` (36 МБ, 25,6 мин, 479 «тяжёлых» окон `[gpu-perf]` с draws > 300).
База: `…_2026-10-20_22-17-46.txt` (C2 без G1, 5,6 мин, 74 тяжёлых окна).
Разбор — потоковый Python: `tools/ds3perf/` (`parse.py <лог> <json>` → `phases.py <json>`, `bins.py <json> 60`, `threads.py <лог> <tid главного>`).
Время у строк без метки — по последней `[xp] hh:mm:ss`. Счётчики-накопители считаются как max(в окне) − max(до окна), потому что строки разных потоков
приходят не по порядку (первая версия скрипта суммировала скачки и завышала компиляции в 15 раз — исправлено).

Пометки: **[факт]** — посчитано из журнала / прочитано в коде; **[оценка]** — арифметика на фактах с допущением (допущение названо); **[версия]** — не измерено.

## Главное

1. **Главный поток (00ac) не загружен целиком: 61–66 % ядра** [факт]. После нагрева кадр 51,8 мс, из них главный поток работает 31,5 мс, GXWorker'ы по 10,9 мс каждый (5 штук), GPU занят 52 %.
   Падение 28 → 19,3 FPS = частота P-ядер 2,20 → 1,60 ГГц (−27 %) **плюс** работы на кадр больше (104 → 122 млн инструкций главного потока, draws 526 → 619) [факт].
2. **Всё, что G1 целил, убрано** [факт]: нарушений доступа 38,8 → 4,1 на кадр, SMC-записей 23,8 → 4,7, сбросов стека возвратов 50 → 11,5, компиляций FEX 137 → 23, запросов к wineserver 11 600/с → 490–680/с. Убирать дальше `mach_vm_region` из обработчика исключений и стек-дамп раз в 20 с **уже не стоит** — это доли процента.
3. **Новое: DXMT создаёт и уничтожает 15–30 тыс. Metal-буферов в секунду (~1 000 на кадр, в среднем 438 байт)** [факт: счётчики DXMT] — переименования динамических буферов, у которых «запас» обрезается до 64.
   И **~960 раз/с выделяет и освобождает 2 МБ** под каждый список команд отложенного контекста [факт]: каждое = выделение памяти в Wine + сброс 2 МБ в FEX на всех ~100 гостевых потоках под общим замком.
   Обе вещи лежат на главном потоке и на GXWorker'ах. Оценка цены — 6–17 % всего CPU процесса [оценка].
4. Телефон после 4-й минуты упирается в **мощность (~1,2 Вт CPU процесса)**, а не в один поток: при той же мощности минус X % работы CPU ≈ плюс X % FPS (`DS3-POWER.md`). Поэтому считается вся работа процесса (2,5 ядра), а не только главный поток.
5. Собрано (всё за выключенными по умолчанию ключами): `d3d11-g1next.dll` (2 правки DXMT), `ntdll-g1next.dll` (csx64 + урезанный учёт в SRW). Предлагаемый пакет H1 — §6. Честный прогноз: **19 → 21–24 FPS после нагрева** [оценка]; до 30 одним этим пакетом не дойти.

## 3. Что ещё ест CPU — находки

### 3.1 DXMT: ~1 000 новых Metal-буферов на кадр [факт по счётчикам и коду; цена — оценка]

```
218023: [mem-census]   dynamic recycle: reuse-hit=55490215 fresh=30867297 hit-rate=64% | … lag-max=17
218018: [buf-site]   DynamicBuffer::allocate live=17MB / 15532 buffers  avg=1KB  (ever: 30867297 / 13522MB)
218006: [trim] ml685 ALL-instance totals: released 30849679 entries / 13491MB | regret=666 …
```
- По 100-секундным отрезкам: **15–30 тыс. новых буферов/с** (≈ 1 000 на кадр), переименований 45–77 тыс./с; в базе было ~10 тыс./с (≈ 600 на кадр).
- Каждый «fresh» = `Buffer::allocate` → `new BufferAllocation` → `device.newBuffer` (unix-вызов в Metal) и потом освобождение (`dxmt_buffer.cpp:149`, `dxmt_dynamic.cpp:151`).
- Почему: `DynamicBuffer::allocate` держит не больше **64** отработавших имён на буфер (`DYN_KEEP_ELIGIBLE`, `dxmt_dynamic.cpp:98`), лишнее сразу освобождает.
  Буфер констант, который игра переименовывает на каждый draw (~600 draws), каждый кадр теряет запас и создаёт его заново. Освобождено 30,85 млн ≈ создано 30,87 млн.
  Показатель `regret=666` этого не видит: он ловит только промах сразу после обрезки, а после обрезки 64 записи остаются и следующий вызов попадает [факт по коду].
- Ещё на каждый вызов — проход по всей очереди буфера для статистики (до 64 записей × 8 сравнений) [факт по коду].
- Цена [оценка, не мерил]: создание+освобождение маленького общего MTLBuffer через переход в unix ≈ 5–15 мкс → **100–300 мс CPU в секунду** (4–12 % процесса) на главном потоке и GXWorker'ах.

### 3.2 DXMT: 2 МБ на каждый список команд [факт]

```
186331: E AC [iOS-xrem] via=aligned #1268736 tracker=0x14e719300 0x708eb40000-0x708ed50000
172356: [commit-zero] #1196032 GUEST OK base=0x7083400000 size=0x210000 protect=0x4 (zero) checked=1196032/324017 …
```
- 1,47 млн освобождений по 0x210000 байт за прогон = **~960/с, ~50 на кадр**; освобождают GXWorker'ы (77 %, 154–164) и главный поток (23 %).
- Источник: `MTLD3D11CommandList::Reset()` → `cpu_command_allocator.free_blocks(~0)` → `free()` блока 2 МБ (`kStagingBlockSizeForDeferredContext`, `d3d11_context_impl.cpp:5890`); следующая запись → `malloc(2 МБ)`.
  Куча Wine отдаёт блоки ≥ ~1 МБ напрямую из `NtAllocateVirtualMemory` и возвращает `NtFreeVirtualMemory` (`heap.c:169`, `HEAP_MIN_LARGE_BLOCK_SIZE`).
- На каждое освобождение FEX делает `InvalidateAlignedInterval` под **исключительным** `CodeInvalidationMutex` и обходит кэши всех гостевых потоков (~100; `InvalidationTracker.cpp:512`, `Core.cpp:2354`); на каждое выделение — проверка нулей `[commit-zero]` (`mach_vm_read`, под `virtual_mutex`) и первые касания страниц.
- Цена [оценка]: 40–120 мкс на цикл → **40–115 мс CPU/с** (1,5–4,5 %).

### 3.3 Учёт в SRW-замках ntdll [факт по коду; цена — оценка]
`[xp-api]`: `wake1 55–57 тыс./с`, `wakeAll 115–137 тыс./с` = ~190 тыс. освобождений SRW в секунду. На каждый захват и освобождение — `InterlockedIncrement` одного общего счётчика кольца (`ios_srw_note`, `sync.c:897`), на каждый wake/wait — ещё один общий счётчик `ios_xp_nt.woa_*` (`sync.c:1361/1438/1481`).
Итого ~0,5 млн атомарных операций/с над несколькими общими кэш-линиями с 8 потоков на P- и E-ядрах. Цена [оценка, 50–150 нс на операцию при перебросе линии]: 25–75 мс/с (1–3 %).

### 3.4 Исключения теперь [факт + оценка]
~84 нарушения доступа/с (почти все — записи anti-tamper в `.text` exe, 32 «горячие» страницы обслуживает hot-smc v2) + 9 невыровненных/с + ~100 SMC/с.
`mach_vm_region` в обработчике (`signal_arm64_ios.c:2142`): 84/с × 3–10 мкс = **0,3–0,9 мс/с, 0,01–0,04 %** — правка больше не окупается (при 2 700/с в старом логе было 1–3 %).
Остаток SMC: ~100 ловушек/с × 30–80 мкс (сброс кода, снятие защиты, полный круг исключения) ≈ 3–8 мс/с, в основном главный поток (`D AC`) — 0,1–0,3 % [оценка].

### 3.5 Мелочь [факт по частоте, цена — оценка]
- `[thread-stacks]` раз в 20 с: 114–117 потоков, `thread_get_state` без заморозки + обход стеков на служебном потоке, 690 строк журнала за раз (35 строк/с в среднем). < 0,05 %. Ручки нет (`Winios.m:1305`, unix-часть — только через CI) — не делал.
- `[bc-stream]` DXMT: 51 строка/с (одна на 1 024 `UpdateSubresource`) с форматированием в PE и записью через unix — ~0,05 %. В `d3d11-g1next.dll` при `DXMT_CENSUS_THROTTLE=1` раз в 10 с.
- Сбросы стека возвратов FEX 241/с × 20–50 мкс (`madvise` 8 МБ + повторное заполнение) ≈ 5–12 мс/с, 0,2–0,5 %.
- Компиляции FEX ~500/с × 50–110 мкс ≈ 25–55 мс/с (1–2 %); больший буфер кода убрал бы только всплеск после смены (раз в ~400 с, ~минута по 1 000/с) — ~0,3 % в среднем.

### 3.6 Без пересборки [факт по коду, эффект — версия]
- `env.MADEIRA_TLS_X64 = 1` — x64-заглушка `TlsGetValue` **уже собрана в `ntdll-csx64.dll`** (G1 её не включал). Убирает 262 тыс. переходов/с × ~100 тактов ≈ 16 мс/с при 1,6 ГГц ≈ 0,6 % [оценка].
- `env.FEX_TSOENABLED = 0` — потолок выигрыша от модели памяти: 10–25 % работы JIT-кода (`DS3-SW-TSO.md`) [версия]; JIT — ~40–55 % времени главного потока по базовому `[cpu-split]` (`x64 JIT 43 %, ARM64EC images 38 %, native 17 %`). Риск порчи данных/зависаний, поэтому **отдельный прогон, сейв — в бэкап**.
- Multiblock (`FEX_MULTIBLOCK=0`) — скорее минус: компиляций мало (23/кадр), а код станет медленнее. Не пробовать.
- SMC-режим FEX: снять проверки нельзя — anti-tamper реально переписывает код (153 тыс. записей за прогон).
- Кэп FPS: после нагрева упор в мощность, кэп устойчивые FPS не поднимает (`DS3-POWER.md`). Кэп 30 сглаживает первые 4 мин (там 27–32) и чуть отодвигает нагрев; для замера пакета H1 **не менять**, чтобы сравнение с G1 было чистым.

Проверено на Linux-хосте [факт]: обе DLL собрались штатными скриптами (`meson`/`ninja` для d3d11 в `build-g1next`, `make` для ntdll в `src-g1next`), строки ключей и логов есть в бинарях;
у `ntdll-g1next.dll` те же 1 473 экспорта на тех же RVA, что у `ntdll-csx64.dll` (CS-заглушки найдут свои FFS). **На устройстве не проверено.**
Без ключей обе DLL ведут себя как `d3d11-ds3fix.dll` / `ntdll-csx64.dll` [факт по коду]; отличие — `[bc-stream]` реже при `DXMT_CENSUS_THROTTLE=1`.

Установка — как для G1 (`docs/guide.md` §1b–2): перед `sign.sh` положить в `work/Payload/Madeira.app/arm64ec-windows/` `d3d11-g1next.dll` → `d3d11.dll` и `ntdll-g1next.dll` → `ntdll.dll`; `xtajit64-hot2.dll` оставить.
Откат: вернуть `d3d11-ds3fix.dll` и `ntdll-csx64.dll` либо просто удалить строки ключей.

Риски [версия]:
- `DXMT_DYN_KEEP`: больше памяти. Каждое удержанное имя — отдельный MTLBuffer, скорее всего минимум страница 16 КБ: 1 024 имени ≈ 16 МБ на «горячий» буфер констант. Смотреть `[footprint] phys=` (в G1 ~5,7 ГБ) и `[mem-census] … shared=`. Если растёт больше чем на ~300 МБ — `DXMT_DYN_KEEP = 256`.
- `DXMT_CMDLIST_KEEP_BLOCK`: каждый список команд в пуле держит 2 МБ адресов (физически — только тронутые страницы). Безопасность: блок переиспользуется ровно там, где раньше освобождался, указателей в него после `Reset()` нет (до этого он уходил в `free`).
- `MADEIRA_TLS_X64`: на устройстве ещё не запускался ни разу. Если игра не стартует/вылетает сразу — убрать эту строку первой.
- `MADEIRA_SYNC_LEAN`: при разборе зависаний на SRW (`[srw] parked …`) не будет истории владельцев — для такого разбора выключить.

## 6. Следующий пакет на один прогон — H1

G1 (`setG1.cfg`) без изменений + DLL из §5 + четыре строки:
```
# H1 (21.10): меньше созданий Metal-буферов, без 2 МБ на каждый список команд, TlsGetValue и SRW без лишнего (DS3-G1-NEXT.md)
env.DXMT_DYN_KEEP = 1024
env.DXMT_CMDLIST_KEEP_BLOCK = 1
env.MADEIRA_TLS_X64 = 1
env.MADEIRA_SYNC_LEAN = 1
```
Сценарий — как у G1: 20+ минут, те же места, сравнивать **после нагрева** (с 5-й минуты) при той же частоте P-ядер.
Что смотреть (всё есть в журнале с этими ключами):
- FPS тяжёлых сцен после 5 мин (G1: 19,3, p10 14,5) и мс главного потока/GXWorker на кадр в `[xp-t]` (G1: 31,5 / 10,9);
- `fresh/с` в `dynamic recycle` (G1: 15–30 тыс./с) и `[footprint] phys=`;
- `[iOS-xrem] via=aligned #N` — скорость роста N (G1: ~960/с);
- `[xp-api-top]` — `kernelbase.dll+0x6d470` (TlsGetValue) должен пропасть;
- `[xp]` Вт и ГГц — для пересчёта на равную мощность.
Четыре ключа в одном прогоне — сознательно, чтобы не гонять тестера по прогонам; у каждого свой счётчик в журнале, так что вклад разделяется по счётчикам, а FPS — сумма.
`FEX_TSOENABLED=0` в H1 не входит: риск порчи данных, его — отдельным прогоном после H1 и с бэкапом сейва.

## 7. Чего не знаем
- Чем занят главный поток внутри после G1 (JIT / EC-код / unix) и кого он ждёт 40 % кадра: `[cpu-split]` и `[rip-profile]` выключены `LEAN_DIAG`. Один диагностический прогон без `LEAN_DIAG` (G1 + H1, ~5 мин) ответит, стоит ли дальше бить по главному потоку или по GXWorker'ам.
- Реальная цена `newBuffer`/освобождения в Metal на A19 и цена цикла 2 МБ — оценки §3 не мерил; H1 их и измерит.
- Поток 0130 (~10 % ядра, 26–32 млн инструкций на кадр) без имени — не опознан.
- На каком d3d11 сейчас телефон: `d3d11-ds3fix.dll` или `out/d3d11.dll` — обе дают в логе тот же адрес TLS-колбэка (`[tls-life] … d3d11.dll … callbacks=…D8B8`); `d3d11-g1next.dll` собран от ds3fix (ceccaa9), так что подходит в обоих случаях [версия].
