Дата: 20.10.2026. Логи: `logs/ds3/DarkSoulsIII.exe-2026-10-20_20-52-57.txt` (основной, без MetalFX, ~3 мин)
и `_20-03-44.txt` (сверка). Конфиг обоих прогонов одинаковый: `pool-split=1`, `MADEIRA_X64_IMAGE_NOCOPY=1`,
`MADEIRA_LOCK_ORPHAN=stamped`; `inproc-sync` не задан → **fastsync auto, sem=off** (`[fastsync] mode=auto peek=on sem=off`,
`[madsync] … disabled`).
Исходники: `<build-tree>/src` @ b8a21b3 (wine 9129e968, dxmt ceccaa9). Разбор — Python по строкам (`/tmp/ds3h/*.py`, scratch).
**[факт]** — посчитано из лога / прочитано в коде; **[оценка]** — арифметика на фактах; **[версия]** — не измерено.
Время «t» ниже — секунды от первой строки лога (20:52:12).

В этом прогоне номера потоков сдвинуты относительно 20:03: **00b4 = главный поток** (самый занятый в `[xp-t]`, 150–180 мс CPU
на окно 250–300 мс), 0120 = Core.Res.TaskManager, 00c4 = FD4JobWorker:1, 0154 = GXRenderThread, 0140 = dxmt-encode-thr.

## A. Трафик в wineserver

### Формат строк [факт, `build/wineserver/request_ios.c:302–440`]
- `[srv-req] ml1055 last 200000 requests in N s: reqK=count(tid T ~n)` — 10 самых частых запросов за последние 200 000;
  в скобках — самый активный поток (счёт «space-saving», может завышать). Номер → имя по `wine/include/wine/server_protocol.h`.
- `[srv-req] select by shape` — форма ожиданий и **тип первого объекта** (семафор/событие/мьютекс…).
- `[sync-census] ml1115 … server requests N/s` — общий темп (`build/ntdll-unix/server_ios.c:2828`).
- `[srv-doorbell]` — проходы цикла сервера и «звонки» потокам (`build/wineserver/fd_ios.c:1792`).

### Что идёт в сервер в бою (t = 120–160 с, 16.4 с на 200 000 запросов) [факт]

| Запрос | Всего/с | От главного потока 00b4, /с | Win32-источник |
|---|---|---|---|
| `select` (req29) | 6 800 | ~2 150 | `WaitForSingleObject` (почти все — одиночные, не alertable: single 109k из 111k) |
| — первый объект: семафор | 3 100 (47 %) | | ожидание job-системы FD4 |
| — мьютекс | 2 200 (33 %) | | `WaitForSingleObject(hMutex)` |
| — событие | 820 (12 %) | | ожидания, не ушедшие в fastsync (не дождались за 2 мс) |
| `release_mutex` (req37) | 2 200 | ~1 030 | `ReleaseMutex` |
| `release_semaphore` (req41) | 2 100 | ~1 000 | `ReleaseSemaphore` |
| `event_op` (req31) | 640 | ~500 | `SetEvent`/`ResetEvent` при ждущем на сервере |
| `set_cursor` / `get_message` / `get_window_children_from_point` | ~75 / 57 / 38 | все с 00b4 | опрос курсора/окна раз в кадр |
| `create_event` + `get_inproc_sync_fd` + `close_handle` | ~60 / 60 / 60 | | события создаются и закрываются на лету |

- Итого **~12 200 запросов/с** (`[sync-census]` 12 019–12 232/с), при ~19 FPS это **~640 на кадр, из них ~260 от главного потока** [оценка].
- На загрузке (t = 55–85 с) — 25–32 тыс./с, лидер **0120 Core.Res.TaskManager** (select+release_mutex), `[srv-doorbell]` до 42 000 звонков/с.
- `QPC syscalls` 1 200–1 500/с, `NtQueryPerformanceCounter` в сервер **не ходит** — не рычаг. Файловых опросов в топе нет.
- Пара `select(mutex)` ≈ `release_mutex` по числу → это **неконкурентные захват/отпуск мьютекса**: каждый = 2 рейса в сервер.

### Берёт ли fastsync мьютексы — **нет** [факт]
- `include/wine/madeira_fastsync.h`: виды ячеек только `MADEIRA_CELL_KIND_EVENT` и `MADEIRA_CELL_KIND_SEM`.
- `wine/server/mutex.c` не содержит ни одной правки madeira; в `build/wineserver/build.sh` (`PATCHED_FILES`/`REPLACEMENTS`)
  **mutex.c нет** → `mutex.o` берётся из готового архива.
- Мьютексы в процессе умеет только **madsync** (`build/madsync/madsync.c:16–19`: «semaphores, mutexes (recursive, owner-tracked, abandonment)»),
  а он в этих прогонах выключен.

### Какой рычаг что снимает [факт по коду, эффект — оценка]

| Рычаг | select(sem) | select(mutex) | release_mutex | release_sem | event_op/select(event) |
|---|---|---|---|---|---|
| `inproc-sync = 1` (madsync) | да | **да** | **да** | да | да |
| `env.MADEIRA_FASTSYNC_SEM = 1` | да | нет | нет | да | (уже) |
| `env.MADEIRA_SRV_DIRECT = 1` | нет | нет | на потоке вызова | на потоке вызова | event_op — на потоке |
| `env.MADEIRA_SRV_DIRECT = 2` | + select на потоке вызова (без переключений), но под общим замком сервера | | | | |

`SRV_DIRECT` список — `request_ios.c:503–546`. Он не убирает запрос, а убирает два переключения потоков на запрос.

### Правка кода: мьютексы в fastsync (если madsync не подойдёт)
Пересобирается CI: клиент `wine/dlls/ntdll/unix/sync.c` (собирается из сабмодуля, `build/ntdll-unix/build.sh` ветка `*`),
сервер — нужно **добавить `mutex:$WINE_SRC/server/mutex.c:mutex.o` в оба списка** `build/wineserver/build.sh` (иначе правка — мёртвый код, как предупреждает сам скрипт).
Схема (как у семафора, `server/semaphore.c`, ~23 точки правки + ~200 строк клиента):
- ячейка `KIND_MUTEX`: state = TID владельца (0 — свободен), счётчик рекурсии — поле ячейки, пишет только владелец;
- клиент `NtWaitForSingleObject`: CAS 0→TID (или owner==self → count++) — без сервера; `NtReleaseMutant`: count-- / CAS TID→0, при `srv_waiters` — запрос-пробуждение;
- сервер `mutex_sync_signaled/satisfied` читают/пишут ячейку; `abandon_mutexes` при смерти потока сканирует ячейки с owner==TID.
Снимает ~4 400 запросов/с (33 % select + весь release_mutex), с главного потока ~2 000/с ≈ 100 рейсов на кадр →
**+2–5 % FPS** [оценка: 10–20 мкс/рейс]. Брать только если `inproc-sync = 1` ломает игру — он даёт то же и больше без кода.

Сверка на 20:03-44 [факт]: оба больших рывка — **475 мс (t=111) и 372 мс (t=174)** — сразу после `tail BIG` (t=107.0) и `tail REUSE` (t=170.3),
FEX главного потока 19.8 и 17.0 тыс./с, `UNALIGNED-BACKPATCH` +2 100 и +1 800. **3 из 3 крупных рывков = смена буфера кода FEX.**

- **Смена буфера кода** (раз в ~60 с; 128 МБ — потолок FEX по дальности ветвления, `virtual_ios.c:29070`): весь код компилируется заново,
  и заново ловятся невыровненные атомики (каждый — Mach-исключение + патч) [факт по совпадению; вклад backpatch в 475 мс — версия].
  Буфер заполняется так быстро из-за перекомпиляций после SMC-записей anti-tamper (`DS3-SMC-PATCH.md`) [версия, сходится с темпом 2 тыс. компиляций/с].
- **Компиляция пайплайнов DXMT**: в логе **не пишется вообще** (`d3d11_pipeline.cpp` без логов; `pso->GetPipeline(...) // may block`,
  `d3d11_context_impl.cpp:5130`) — сопоставить нельзя.
- **Постоянный кэш шейдеров для DS3 ВЫКЛЮЧЕН** [факт]: в каждом логе (13:21, 20:03, 20:52) `Failed to set Metal cache path, fallback to system default` ×2
  и `[CacheReader] Failed to resolve cache path` ×2. Причина: путь кэша относительный, а `_CS_DARWIN_USER_CACHE_DIR` в песочнице iOS пуст;
  обход `DXMT_IOS_CACHE_DIR` (`dxmt/src/winemetal/unix/cache.c:25–47`) **включён по умолчанию только для 32-бит**, DS3 — 64-бит.
  Значит каждый запуск заново переводит DXBC→Metal; и в Metal уходит `MTLSetShaderCachePath(nil)` (`cache.c:298`) — не отключает ли это
  системный кэш пайплайнов, **не проверено** [версия].
- **`pso-warm`** — только D3D12 (вызов MadeiraCtl op 10 есть лишь в `madeira-d3d12`, в DXMT d3d11 нет) → для DS3 бесполезен [факт].
- Текстуры/куча: `METAL currentAllocatedSize` ровный 1 490–1 600 МБ, в окнах рывков скачков нет; BC на CPU не декодируется (`decoded total=0`) [факт]. Признаков нет.
- `[freeze]`: `gaps=0` за весь прогон [факт].
- **Нагрев**: `nominal → fair` в t=92 (39 FPS). Через ~10 с (t≈100) частота P-ядер 2.8 → 1.6–1.8 ГГц, энергия CPU на окно 780 → 310 мДж,
  а GPU-время кадра 12 → 35 мс при тех же 350–550 draws [факт]. В 20:03 — та же картина в t≈100. Это не рывок, а ступенька 35 → 19 FPS.
  Нагрев или более тяжёлая сцена — **не различить без `MADEIRA_POWER_PROBE`** [версия].
