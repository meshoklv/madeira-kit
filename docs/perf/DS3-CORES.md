# DS3 на iPhone Air: как потоки распределены по ядрам и что можно перенести

Дата: 21.10.2026. Только чтение исходников и лога, на телефоне ничего не запускалось.
Лог: `logs/ds3/DarkSoulsIII.exe-2026-10-21_12-52-56.txt` (конфиг G1, 26 мин; разбор Python потоком, `[xp]`/`[xp-t]` — 4 944 строки).
Исходники: `<build-tree>/src` (ci-build), FEX `<build-tree>/fex-src` @ f59cab9.
Пометки: **[факт]** — посчитано из лога или прочитано в коде; **[источник]** — из внешней статьи;
**[оценка]** — арифметика на фактах с допущением; **[версия]** — не измерено.
Покадровый разбор работы главного потока ведёт отдельный документ (`DS3-G1-NEXT.md`); здесь только потоки и ядра.

## 0. Итог

1. **E-ядра простаивают, P-ядра забиты и зажаты.** После зажима (с ~5-й минуты) P-ядра работают на **1,69 ГГц**
   (пик в этом же логе — 4,21 ГГц) и заняты на **84 %** (1 680 мс/с из 2 000). E-ядра — на **2,17 ГГц**
   (почти их максимум) и заняты на **22 %** (895 мс/с из 4 000). Ещё 335 мс/с потоки стоят в очереди за ядром. [факт]
2. **Главный поток (00ac) 19 % своего времени работает на E-ядрах** (119 мс/с из 610), где он в 2–2,5 раза
   медленнее. Почти всё время (98 % замеров) остальные потоки игры держат больше одного P-ядра. [факт]
3. **Главного потока теснят пять GXWorker'ов игры**: вместе 1 043 мс/с, из них **669 мс/с на P-ядрах** —
   больше, чем сам главный поток (491). Все потоки приложения сейчас **одного класса USER_INTERACTIVE**:
   Madeira поднимает так каждый гостевой поток и игнорирует приоритеты, которые выставляет игра. [факт]
4. Что можно сделать без правки файлов игры, по выгоде:
   - **поставить главный поток выше остальных** (градиент QoS по имени потока). Главный поток — USER_INTERACTIVE,
     GXWorker — USER_INITIATED, фоновые пулы — UTILITY. Выигрыш **+5–15 % FPS** [оценка], правка ~100 строк в ntdll;
   - **замер энергии по потокам** (`env.MADEIRA_POWER_PROBE = 1`) — бесплатно, решает, есть ли смысл гнать работу на E-ядра ради ватт;
   - DXMT кодирование **уже** на отдельном потоке, wineserver **уже** USER_INTERACTIVE, Game Mode **уже** объявлен — там почти нечего брать;
   - перенос компиляции FEX в фон или кэш на диск — крупный выигрыш, но это месяцы работы (в FEX кэш кода сырой, а для Windows-сборки не подключён).
5. **Честно про 30 FPS:** главный поток тратит **~28 мс CPU на кадр** при 21,5 FPS и ещё ~18 мс на кадр ждёт.
   Перераспределение потоков даёт порядка **22–25 FPS** в тяжёлых сценах после зажима [оценка].
   Для устойчивых 30 нужно ещё и урезать работу главного потока (это тема `DS3-G1-NEXT.md`) или поднять частоту P-ядер
   (это питание и нагрев, см. `DS3-POWER.md`).

## 2. Как iOS раскладывает потоки и что может приложение

**Классы QoS** (база приоритета): USER_INTERACTIVE 47, USER_INITIATED 37, DEFAULT 31, UTILITY 20, BACKGROUND 4
[факт: комментарий `server_ios.c` у power probe]. На Apple silicon, по замерам Оукли на macOS [источник]:
- **BACKGROUND и ниже — только E-ядра**, даже когда P-ядра простаивают;
- **UTILITY и выше — предпочитают P-ядра**, на E уходят, только когда P заняты; тогда E-ядра поднимают частоту;
- **привязки к ядрам нет** ни у разработчика, ни у пользователя (`thread_policy_set(THREAD_AFFINITY_POLICY)` на arm64 не работает).

Для iOS отдельных замеров не нашёл — **[версия]**: планировщик тот же (XNU Edge + CLPC), поведение похожее.
Отсюда главное: **понижение до UTILITY/USER_INITIATED на E-ядра поток не переносит** — оно лишь даёт ему меньший
приоритет, когда за P-ядро спорят. Переносит только BACKGROUND, но он ещё и душит частоту и ввод-вывод — для потоков,
которых ждёт кадр, не годится.

Что ещё есть у приложения:

| Ручка | Что делает | В Madeira | Для DS3 |
|---|---|---|---|
| `pthread_set_qos_class_self_np` | класс QoS — **только на самого себя** | все гостевые потоки → USER_INTERACTIVE (`thread_ios.c` start_thread → `ios_eco_apply_self`, `sync.c:2199`) [факт] | рабочий рычаг, см. §4 |
| `pthread_attr_set_qos_class_np` | класс при создании | сервер Wine, мост процессов — USER_INTERACTIVE (`WineServerBridge.m:171`, `WineProcessBridge.m:1929`) [факт] | уже на максимуме |
| SetThreadPriority игры | Windows-приоритеты | **игнорируются**: `[thread-prio] … kept at pthread QoS` (`wine/server/thread.c:309`); `MADEIRA_WIN_THREAD_PRIORITY=1` включает старый перевод в Mach-политики [факт] | что ставит сама DS3 — не видно: лог печатает только первые 24 потока, игровые туда не попали [факт] |
| DXMT SetThreadPriority | TIME_CRITICAL → USER_INTERACTIVE, NORMAL → INITIATED, ниже → UTILITY (`util_madeira_compat.h:141`) | encode/finish/компиляция шейдеров = USER_INTERACTIVE [факт] | уже на максимуме |
| Режим ECO (`eco = 1`, `eco-qos`) | **все** гостевые потоки, включая главный → UTILITY/BACKGROUND (`sync.c:2172`) | выкл. [факт] | без разбора, главный поток проигрывает вместе со всеми |
| `MADEIRA_BG_QOS_PROCS` | процессы лаунчера → UTILITY, пока игра рисует | срабатывает только при роли P, которую ставит лишь madeira-d3d12; в DS3 строк `[bg-qos]` 0 [факт] | Steam и так простаивает (`DS3-BG-PROCS.md`) |
| `MADEIRA_ECO_NATIVE=1` | служебные нативные потоки Madeira → UTILITY | выкл. в G1 [факт] | они почти не едят: wine-x18-exc 0,6 мс/с [факт] |
| Realtime (`THREAD_TIME_CONSTRAINT_POLICY`) | реальное время | только аудио (`audio_null_ios.c:1303`) [факт] | для главного потока опасно: ядро понижает поток, превысивший заявленное время |
| `os_workgroup` / `AudioWorkIntervalCreate` | интервал с дедлайном → CLPC поднимает частоту под срок | нет [факт] | официально — для потоков реального времени аудио [источник Apple]; для игры — эксперимент, потолок питания не снимает [версия] |
| Game Mode (`GCSupportsGameMode`, `LSSupportsGameMode`, категория games) | приоритет CPU/GPU игре, фон приглушён | **уже объявлен** в `Info.plist:41-46` [факт] | включился ли на телефоне — не проверял |
| CADisplayLink `preferredFrameRateRange` | частота экрана | оверлей FPS, «жидкий металл» UI 30–60 Гц (`GlassSkin.swift:85`) [факт] | на ядра не влияет |

## 3. Кто где работает (лог 21.10, G1)

Формат `[xp-t]` (`server_ios.c:2598`): `<роль|->ТИД:P мс/E мс:ГГц P/ГГц E:млн инструкций` за окно ~250–320 мс;
печатаются 14 самых занятых потоков (≥ 2 мс). Покрытие ~85 % CPU процесса [факт].
`[xp] run=` — время, когда потоки готовы к работе, **включая** само выполнение (в первом замере run 271 ≈ cpu 262 при пустых E-ядрах),
поэтому «run − cpu» = **ожидание ядра в очереди** [факт по логу; трактовка сходится с комментарием в `server_ios.c:1724`].

Наблюдения:
- **GXWorker'ы — главные соседи главного потока по P-ядрам.** Они того же класса USER_INTERACTIVE, поэтому
  планировщик не отличает их от главного потока, и тот 19 % времени выталкивается на E-ядра [факт].
- **Главный поток занят не всё время**: 610 мс/с при 21,5 FPS ≈ **28 мс CPU на кадр**, кадр 46 мс → ~18 мс на кадр он ждёт
  (GPU, рендер-поток, GXWorker'ы — что именно, покажет покадровый разбор) [оценка].
- **Переходы x64→EC — ~700 тыс./с**, из них заметная часть — вызовы `d3d11.dll` (≈ 10 из 28 верхних адресов `[xp-api-top]`).
  Будильников WaitOnAddress — **~236 тыс./с** (wake1 94 тыс. + wakeAll 142 тыс.) [факт]. Это цена на поток вызывающего; разбор — в `DS3-G1-NEXT.md`.
- dxmt-encode-thr вызывает QueryPerformanceCounter **17,6 тыс. раз/с** (77 % всех вызовов QPC в процессе) [факт, `[xp-api-qpc]`] —
  это таймеры статистики DXMT; поток не главный, цена мелкая [оценка].

## 4. Что можно перенести или переставить (без правки файлов игры)

### 4.1 Градиент QoS по имени потока — главный рычаг [код прочитан; эффект — оценка]

Сейчас все гостевые потоки — USER_INTERACTIVE. Нужно, чтобы главный поток выигрывал каждый спор за P-ядро.
**Прав понизить главный не нужно — нужно понизить соседей**:

| Класс | Потоки (по `[thr-name]`) |
|---|---|
| USER_INTERACTIVE (как сейчас) | главный 00ac, GXRenderThread, dxmt-encode/finish, wine-x18-exc, сервер Wine |
| USER_INITIATED (всё ещё предпочитает P-ядра, но уступает главному) | GXWorker:* |
| UTILITY | FD4JobWorker:*, Core.Res.*, EzWorkPool_*, Bnd4FSAsync, NexusRevolution*, HkAiThread*, CSChrBackInitialize*, потоки Steam (dockhost), wine_*-служебные |

Как сделать (≈ 100 строк, только ntdll, сборка CI) [факт по коду, где цепляться]:
- имя потока приходит в `set_native_thread_name` (`build/ntdll-unix/thread_ios.c:2643`, уже пишет `[thr-name]`);
  часто его ставит **не сам поток** («NOT self» в логе), а QoS ставится только на себя;
- поэтому: таблица `тид → желаемый класс` по шаблонам из `env.MADEIRA_THREAD_QOS` (например
  `GXWorker*=initiated;FD4JobWorker*=utility;…`), а поток применяет класс сам на ближайшем ожидании —
  тем же механизмом, что ECO (`IOS_ECO_POLL` в `sync.c`), только с поправкой «свой класс вместо общего»;
- главный поток игры определить как поток, запустивший процесс exe (его тид известен: `signal_start_thread … peb=` игры), а не по имени — у 00ac имени нет;
- строка в лог `[thread-qos] тид имя → класс`, откат — пустая переменная.

Ожидание [оценка]:
- главный поток уходит с E-ядер: 119 мс/с на E ≈ 48–67 мс/с на P → **−53…−71 мс/с** его времени (−8…−12 %);
- плюс его доля очереди (весь процесс стоит в очереди 335 мс/с; доля главного неизвестна — [версия] 30–60 мс/с);
- итого главный поток короче на **8–20 %** → **+5–15 % FPS**, если кадр упирается в него.
- **Риск — средний**: если главный поток ждёт результатов GXWorker'ов, а те станут медленнее, выигрыш съестся
  или уйдёт в минус. Поэтому первый прогон — GXWorker'ы = USER_INITIATED (они всё ещё предпочитают P-ядра),
  UTILITY — только фоновым пулам. По одному изменению за прогон, с `[xp-t]`.

Бесплатная проба до правки кода: `env.MADEIRA_WIN_THREAD_PRIORITY = 1` — вернёт Windows-приоритеты игры через
политики Mach. Что ставит DS3 своим потокам — неизвестно (лог `[thread-prio]` обрезан на 24 строках); если игра не
различает главный поток и рабочие, градиента не будет, а все потоки получат поправки «ниже USER_INTERACTIVE»
[версия]. Ожидание низкое; полезно только как разведка, если поднять лимит лога.

### 4.2 Перенос работы на E-ядра ради ватт — сначала замер [версия]

Логика: P-ядра зажаты по **мощности**, а не по температуре ядра (`DS3-POWER.md`). Если часть работы GXWorker'ов
(669 мс/с на P) выполнится на E-ядрах дешевле по энергии, P-кластер получит больше ватт и поднимет частоту для главного потока.
Но **при 1,69 ГГц P-ядро может быть почти так же экономно, как E-ядро на 2,2 ГГц** — что выгоднее, логи не говорят
(регрессия энергии по `[xp]` неустойчива). Ответ даст **`env.MADEIRA_POWER_PROBE = 1`**: раз в 5 с строка `[power-t]` с энергией
каждого потока на P и E и его базовым приоритетом (`server_ios.c:2140–2160`) [факт по коду].
Принудительно отправить поток на E можно только через BACKGROUND — для GXWorker'ов не годится (их ждёт кадр).

### 4.3 DXMT: кодирование команд уже не на вызывающем потоке [факт]

- `ASYNC_ENCODING 1` (`dxmt_command_queue.cpp:11`): вызывающий поток только записывает команды в «чанк», а Metal-кодирование
  и `commit` делает **dxmt-encode-thr** (`EncodingThread`, строка 151), ожидание GPU — **dxmt-finish-thr** (строка 170),
  компиляция шейдеров — пул из 2 потоков (`dxmt_tasks.hpp`). Это аналог CS-потока DXVK.
- На вызывающем потоке остаются проверка состояния и запись команды (`d3d11_context_impl.cpp`, `EmitST`).
  Кто в DS3 зовёт `d3d11` — GXRenderThread или GXWorker'ы — по логу не видно [версия]; главный поток, судя по объёму
  (encode-поток всего 97 мс/с), тратит на DXMT мало [оценка].
- Ещё один поток кодирования ничего не даст: encode-поток занят ~10 % [факт].
- Мелочь: QPC-статистика DXMT на encode-потоке (17,6 тыс./с) — **≈0** для главного потока.

### 4.4 FEX: компиляция в фоне или с диска [факт по коду; выигрыш — из соседних разборов]

- Компиляция FEX синхронная, на том потоке, который наткнулся на непереведённый код (`[CB_SUMMARY]` печатает поток игры) [факт].
  Фонового компилятора в FEX нет.
- Кэш кода на диске: в FEX есть `EnableCodeCachingWIP` / `EnableLazyCodeCachingWIP` (`Config.json.in:19`), **по умолчанию выкл.**,
  а в Windows-части загрузка не написана: `ImageTracker.cpp:175` и `:283` — `TODO: CodeCache::LoadCache` [факт].
  anti-tamper переписывает код (~24 записи на кадр, `DS3-PERF-next.md`), значит закэшированные блоки в этих страницах будут сбрасываться.
- Цена компиляций на главном потоке — **4–9 мс на кадр** [оценка из `DS3-PERF-next.md`]. Довести кэш до рабочего — недели-месяцы, риск высокий.

### 4.5 Сервер Wine, аудио, Steam, интерфейс [факт]

- Сервер Wine уже USER_INTERACTIVE (`WineServerBridge.m:171`); с `inproc-sync = 1` запросов к нему **473/с** (было 13–17 тыс./с в
  старых прогонах). Брать нечего.
- Аудио (audio_client_main/timer, AURemoteIO) и Steam — в топ-14 не попадают (< 2 мс/с).

## 6. Сделано: `MADEIRA_THREAD_QOS` — класс QoS по имени потока (21.10)

Пункт 2 из §5. Коммит `8922c45` в форке `meshoklv/Madeira`, ветка `ci-build`, сборка CI — `builds/Madeira-gh-8922c45.zip`
(прогон 39546454311, успех, 10 мин). Только нативная часть ntdll (её собирает CI), DLL Windows не тронуты. **По умолчанию выключено.** [факт]

**Где правка** [факт, код]:
- `build/ntdll-unix/thread_ios.c` — разбор переменной, таблица «тид → класс, имя», обёртка `madeira_guest_qos_self`;
  крючки в трёх местах: `set_native_thread_name` (поток получил имя), `start_thread` (поток стартовал — вдруг его назвали раньше),
  выход потока (тид освобождается, чтобы новый поток с тем же номером не унаследовал класс);
- `build/ntdll-unix/build.sh` — `sync.c` из подмодуля wine компилируется с `-Dpthread_set_qos_class_self_np=madeira_guest_qos_self`.
  Так `ios_eco_apply_self` (через неё каждый гостевой поток ставит себе USER_INTERACTIVE при старте и при переключении ECO)
  идёт через обёртку. Подмодуль wine не меняется (CI берёт его закреплённый коммит 9129e96 из willfaust/wine).

**Как работает:**
- `env.MADEIRA_THREAD_QOS = шаблон=класс;шаблон=класс;…`; шаблоны с `*` и `?`, регистр важен, срабатывает первый подходящий;
  классы `user-interactive`, `user-initiated` (`initiated`), `default`, `utility`, `background`. Неизвестный класс — строка
  `[thread-qos] ignored rule …`, остальные правила работают.
- Поток без имени (главный 00ac) и поток без подходящего правила (GXRenderThread, dxmt-*, аудио) остаются USER_INTERACTIVE.
- QoS можно ставить только себе. Поток, назвавший сам себя (DS3 называет свои потоки так, но через настоящий дескриптор —
  отсюда «NOT self» в `[thr-name]`; тид сверяется запросом к серверу), получает класс сразу. Поток, которого назвал другой, — на
  ближайшем ожидании/сне/уступке: счётчик ECO сдвигается, и все потоки один раз заново ставят себе класс.
- Включённый ECO главнее: в ECO все потоки в классе ECO, как раньше; после выключения ECO классы по именам возвращаются.
- В журнал: одна строка при разборе `[thread-qos] MADEIRA_THREAD_QOS: N rule(s)` и одна на поток
  `[thread-qos] 0154 GXWorker:1 -> user-initiated` (с `REFUSED…`, если iOS отказала).
- Переменная не задана — обёртка отдаёт класс без изменений, сервер не опрашивается, счётчик ECO не трогается: поведение прежнее.

**Проверено** [факт]: логика (разбор, шаблоны, «сам/другой назвал», «назвали до старта», ECO вкл/выкл, переименование,
повторный тид, переменная не задана) — тестом на Linux-хосте (gcc, заглушки вместо iOS); компиляция под iOS — CI 39546454311: ntdll 37 из 37, `thread.c` без предупреждений, обёртка `madeira_guest_qos_self` есть в бинаре.
**Не проверено:** на телефоне не запускалось; что iOS действительно двигает потоки так, как в §2, — [версия].

**Строка для прогона** (`setH2.cfg` = H1 + эта строка):
```
env.MADEIRA_THREAD_QOS = GXWorker*=user-initiated;FD4JobWorker*=utility;Core.Res.*=utility;EzWorkPool*=utility;Bnd4FSAsync*=utility;NexusRevolution*=utility;HkAiThread*=utility;CSChrBackInitialize*=utility;FaceGenMan*=utility
```
По журналу 21.10 она ловит 5 GXWorker → user-initiated и 38 фоновых потоков → utility; главный, GXRenderThread, dxmt-encode/finish,
SprjClothVertexUpdateThread, аудио, ввод и потоки Steam не трогает [факт, сверено с `[thr-name]`].

**Что смотреть в журнале H2:** ~44 строки `[thread-qos]` (43 потока плюс строка разбора); в `[xp-t]` доля P у 00ac (было 81 %) и его мс на кадр; FPS `[gpu-perf]`
после нагрева (было 19,3–21,5); мс/с GXWorker'ов на P (было 669).

**Риски:**
- если кадр ждёт GXWorker'ов или FD4JobWorker'ы, их понижение удлинит кадр — FPS может упасть (§4.1). Тогда первым убрать `FD4JobWorker*=utility`,
  вторым — GXWorker'ов вернуть в `user-interactive`;
- шаблон шире задуманного заденет чужие потоки (например `*Thread*` поймает GXRenderThread) — сверять по строкам `[thread-qos]`;
- со сборками старше `8922c45` строка ничего не делает (молча);
- при ECO и `MADEIRA_BG_QOS_PROCS` (лаунчеры) классы по именам не применяются — те ставят свой класс.
