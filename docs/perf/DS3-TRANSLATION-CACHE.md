## 0. Итог

1. **Писатель один, целей мало и они всегда одни и те же.** [факт] Каждая 100-я ловушка
   (`[mach-deliver]`), 641 выборка из 7 прогонов: всего **33 разных адреса**, 20 из них дают 93 % ловушек,
   одни и те же адреса во всех прогонах (exe всегда грузится по 0x140000000). **32 из 33 адресов ≡ 0xA
   по модулю 16.** Запись — **4 байта**, одна инструкция `STUR w1,[x6]` (0xb80000c1) с адресом,
   зашитым в трансляцию константой (697 из ~820 разобранных `insn_stream`). У гостя это `mov dword
   [rip+X], edx`, а не цикл расшифровки по байтам.
2. **Сразу за записью трансляция опять собирает тот же адрес** [факт: 697/697 случаев, `movz/movk x6`
   после store совпадают с адресом ловушки] — следующая гостевая инструкция снова обращается к тому же
   двойному слову. Если это вторая запись, которая возвращает старое значение («пропатчил → исполнил →
   вернул»), то **«93 % записей меняют байты» не опровергает гипотезу о циклах**: счётчик видит только
   первую, пойманную запись (вторая в ту же страницу проходит через Wine без ловушки), а важно, какие
   байты лежат **в момент перекомпиляции**. [версия — проверяется логированием из §1.3]
3. **Нынешних логов не хватает**, чтобы подтвердить или опровергнуть цикл: значения не пишутся,
   подробные строки `[smc-same]` (24 шт.) — это всё стартовые побайтовые записи. Нужна добавка
   примерно в 20 строк (§1.3) и один прогон.
4. **Выигрыш** [оценка]: если состояния повторяются — перекомпиляций от SMC почти не останется
   (~1 000/с → десятки в секунду, −95…99 %); если это счётчик (значения не повторяются) — минус
   все блоки страницы, кроме тех, что накрывают 4 записанных байта (−60…85 %). Сама ловушка и сброс
   стека call-ret остаются при любом кэше.
5. **Чем дешевле всего** [оценка]: «горячие слоты» — помнить ~33 адреса, блоки поверх них
   компилировать с проверкой байт на входе (механизм в FEX уже есть: `ForceFullSMCDetection`, его так же
   используют для Mono), а запись в слот **не инвалидирует** страницу. Убирает и перекомпиляции, и сброс
   call-ret, и `NtProtect`. Кэш по хешу — хорошая вторая ступень. Оба варианта требуют пересборки
   `xtajit64.dll`, которую CI не делает.

### 1.2 Адреса, писатели, размеры [факт]

- Ловушки, которые реально бьют в устойчивом режиме: 33 адреса (см. §0), топ:
  0x14011538a (100 выборок, 5 прогонов), 0x1402de38a (46), 0x140424f5a (44), 0x1404713ea (41),
  0x1406074fa (36), 0x14048518a (33, 6 прогонов), 0x14062fb0a (33), 0x1404d8eea, 0x14034156a,
  0x14001501a, 0x1404ab05a, 0x14045ec4a.
- Один адрес = одна страница: в выборке прогона 20-52-57 18 адресов на 18 страниц. Значит, на страницу
  приходится один «слот», и каждая ловушка выкидывает всю страницу ради 4 байт.
- Писатель — хост-PC в буфере кода (0x16…/0x17…), поэтому разный между прогонами и поколениями буфера.
  Гостевой RIP пишущего кода в логе есть только у старого `[fault_rip]` (DS3-SMC.md: 65 разных RIP на
  41 500 ловушек, тройки «RIP → цель» стабильны, напр. 0x1408f9b5c → 0x14060fdca). `[smc-write]`
  гостевых вызывающих не показывает (`retRIP=0`).
- Размеры: устойчивый режим — 4 байта (`b80000c1`, реже `b80000c8`); стартовая пачка — 1 байт
  (`38000028` STURB, `19000028` STLURB) — это 24 подробные строки `[smc-same]`, все SAME, все на
  0x1404ea… и пр., пишет один и тот же код (0x17e55c46c/0x17e555580).
- Адрес ≡ 0xA mod 16 у разных функций — похоже на одинаковую раскладку вставок anti-tamper
  (например, `jmp/call rel32` с опкодом по +9 и смещением по +0xA). [версия — проверяется байтами
  вокруг адреса, §1.3]
- «Handled inline self-modifying code» (писатель в той же странице, что и цель) — 40 раз за прогон,
  только на старте. [факт]

### 1.3 Что дописать в счётчик (signal_arm64_ios.c, ветка exp/smc-same-bytes)

Цель: для каждого слота понять, **возвращается ли он к прежним байтам к моменту следующей ловушки**.
Следующая ловушка на тот же адрес бывает только после перекомпиляции страницы (компиляция снова ставит
защиту), а до неё любая запись ловится, — значит «старые байты при ловушке N+1» = байты, из которых
компилировалась страница. Если они совпадают со «старыми при ловушке N», кэш по содержимому попал бы.

1) `ios_smc_same_check`: добавить выход нового значения (последний аргумент `uint64_t *new_out`) и
   перед `return memcmp(...)`:

```c
    if (new_out) { *new_out = 0; memcpy( new_out, val, n > 8 ? 8 : n ); }
```

2) В `bus_handler`: объявить `uint64_t s_new = 0;` рядом с `s_ea`, передать `&s_new` в `ios_smc_same_check`; сразу после вычисления `s_res`:

```c
    /* exp/smc-cycle v1: does a code slot come back to a byte state it had before? */
    static struct { uint64_t ea, old8, first8; unsigned hits, old_rep, toggle, back_first; } cyc[64];
    if (s_res >= 0 && s_n <= 8)
    {
        unsigned h = (unsigned)(((s_ea >> 1) * 0x9E3779B97F4A7C15ull) >> 58);
        uint64_t old8 = 0;
        memcpy( &old8, (const void *)(uintptr_t)s_ea, s_n );          /* whole access already proven inside the page */
        if (cyc[h].ea != s_ea)
        {
            const unsigned char *b = (const unsigned char *)(uintptr_t)s_ea;
            memset( &cyc[h], 0, sizeof(cyc[h]) ); cyc[h].ea = s_ea; cyc[h].first8 = old8;
            if (((s_ea - 10) & ~0x3fffull) == (s_ea & ~0x3fffull))     /* once per slot: what instruction holds it */
                dprintf( 2, "[smc-cyc] new slot %#llx n=%u bytes[-10..+5]=%02x %02x %02x %02x %02x %02x %02x %02x %02x %02x | %02x %02x %02x %02x %02x %02x\n",
                         (unsigned long long)s_ea, s_n, b[-10],b[-9],b[-8],b[-7],b[-6],b[-5],b[-4],b[-3],b[-2],b[-1], b[0],b[1],b[2],b[3],b[4],b[5] );
        }
        else
        {
            cyc[h].old_rep    += old8 == cyc[h].old8;    /* same bytes as at the previous trap = state repeats at compile time */
            cyc[h].toggle     += s_new == cyc[h].old8;   /* writes back what was there last time: A<->B */
            cyc[h].back_first += old8 == cyc[h].first8;  /* returns to the very first state */
        }
        cyc[h].hits++; cyc[h].old8 = old8;
    }
```

3) В печать `totals` (раз в 4 096):

```c
    for (int i = 0; i < 64; i++) if (cyc[i].hits >= 8)
        dprintf( 2, "[smc-cyc] ea=%#llx hits=%u old_rep=%u toggle=%u back_first=%u old=%016llx\n",
                 (unsigned long long)cyc[i].ea, cyc[i].hits, cyc[i].old_rep, cyc[i].toggle, cyc[i].back_first,
                 (unsigned long long)cyc[i].old8 );
```

Как читать: `old_rep/hits ≈ 1` → страница всегда компилируется из одних и тех же байт → кэш по
содержимому попадает почти всегда; `toggle` высокий → классика A↔B; всё ≈ 0 и значения растут →
счётчик/таймер, кэш спасёт только соседние блоки. Байты `[-10..+5]` скажут, код это (`E8/E9`, `FF 25`,
`mov`) или данные внутри `.text`. Таблица без атомиков — допустимо для диагностики (по DS3-SMC.md все
ловушки на главном потоке). Объём: ~25 строк.

## 2. Сколько можно выиграть

Обозначения: C ≈ 4.5…7 компиляций на ловушку [факт], k — блоков, которые накрывают 4 записанных байта
(не измерено; из-за мультиблоков FEX может быть от 1 до C).

| Сценарий | Компиляций на ловушку | SMC-компиляций/с при 240 ловушках/с |
|---|---|---|
| Сейчас | C ≈ 4.5…7 | ~1 100…1 700 |
| Пропуск одинаковых записей (b8a21b3, `MADEIRA_SMC_SAME_SKIP=1`) | C × 0.93…0.999 | почти без изменений (одинаковых в геймплее 0.1 %) |
| Точная инвалидация (только блоки поверх записи), без кэша | k | 240…1 100 |
| Кэш по содержимому, состояния **повторяются** | → 0 после прогрева (33 слота × 2–3 состояния × C ≈ сотни компиляций за всю сессию) | **десятки в секунду (−95…99 %)** |
| Кэш по содержимому, значения **не повторяются** | k (остальные блоки страницы попадают — их байты не менялись) | 240…1 100 (−0…80 %, при k = 1 −80 %) |

Время [оценка]: компиляция ~110 мкс (DS3-SMC.md, межпрогонная оценка), попадание в кэш —
сравнение байт блока (<1 мкс) + вставка в таблицы под замком + повторная защита страницы
(`NtProtectVirtualMemory`, 5–10 мкс; её и сейчас делает каждая компиляция) ≈ **10–15 мкс**. При
1 000 компиляций/с это ~110 мс/с → ~10–15 мс/с, т.е. при ~10 FPS **−4…9 мс на кадр** (сходится с вашей
оценкой стоимости). Не уходит при кэше: сама ловушка (240/с × 30–80 мкс = 7–19 мс/с) и сбросы call-ret
(~500/с, каждый — освобождение 8 МБ + повторные страничные промахи при заполнении) — их убирает только
вариант «не инвалидировать» (§4).

## 3. Где жить кэшу в FEX и как его устроить

Всё в `xtajit64.dll` (`app/Madeira/arm64ec-windows/`, собирается из `Source/Windows/ARM64EC` + FEXCore,
CI её **не** пересобирает — DS3-SMC-PATCH.md §2).

Как сейчас [факт по коду]:
- Ловушка → `InvalidationTracker::HandleRWXAccessViolation` (`Source/Windows/Common/InvalidationTracker.cpp:512`)
  → `InvalidateIntervalInternalLocked(страница 4 КБ)` (стр. 776) → `CTX.InvalidateCodeBuffersCodeRange`
  + `InvalidateThreadCachedCodeRange` для каждого потока (`FEXCore/Source/Interface/Core/Core.cpp:2317,2333`).
- `GuestToHostMap::InvalidateRange` (`LookupCache.h:150`) по `CodePages[page]` стирает **все** точки входа
  страницы: `Erase` рвёт входящие связи блоков (`BlockLinks`) и удаляет из `BlockList`. Кэши потоков
  (L1/L2) чистятся `InvalidateCacheRange`; если что-то было — `ResetCallRetStack` (Core.cpp:737,
  `VirtualDontNeed` на весь стек call-ret).
- Хост-код при этом **не освобождается**: буфер кода — «бамп»; память живёт до смены буфера
  (`ClearCodeCache`, поколения буфера на iOS, `IosMaybeSweepCodeBuffers`).
- Компиляция: `CompileBlock` → `FindBlock` промах → `CompileCode` → регистрирует страницы
  (`AddBlockExecutableRange` + `MarkGuestExecutableRange` = снова ловушка) и точки входа
  (`AddBlockMapping` для каждой из `CompiledCode.EntryPoints`) — Core.cpp:2150–2275.
- Точные гостевые диапазоны блока известны при компиляции: `Frontend::DecodedBlockInformation::Blocks[]`
  (`Entry`, `Size`) — `Frontend.h:39–55`.

Проект «кэш по содержимому»:
1. **Запись при компиляции.** В `GuestToHostMap` (он один на буфер кода — значит, кэш сам умирает вместе
   с буфером, и ссылки на хост-код всегда живые) хранить для мультиблока: точки входа (guest→host),
   список страниц, диапазоны `Blocks[]` и **копию гостевых байт** этих диапазонов (а не только хеш —
   сравнение `memcmp` исключает коллизии; объём — сотни байт на блок, только для блоков на страницах,
   которые хоть раз ловили запись).
2. **При инвалидации** `InvalidateRange` не выбрасывать запись, а переносить её в боковую таблицу
   `retired[GuestRIP] → до 4 вариантов` (вытеснение по давности). Связи рвутся как сейчас.
3. **При промахе** в `CompileBlock` (после `FindBlock`, до `CompileCode`): если в `retired` есть варианты
   для RIP — сравнить сохранённые байты с текущими гостевыми; совпало → повторить ровно хвост
   `CompileBlock` для публикации: `AddBlockExecutableRange` + `MarkGuestExecutableRange` (иначе страница
   останется без ловушки!), `AddBlockMapping` для всех точек входа. Не совпало → обычная компиляция.
4. Проще первая ступень — **точная инвалидация**: на ловушке известен адрес и размер записи (Wine уже
   декодирует store), стирать только мультиблоки, чьи `Blocks[]` пересекают `[ea, ea+n)`; страницу при
   этом **не** снимать с ловушки, пока на ней остались живые блоки.

Объём и риски [оценка]: 300–500 строк в `LookupCache.h`, `Core.cpp`, `InvalidationTracker.cpp`;
2–4 дня с отладкой на устройстве, плюс налаживание сборки `xtajit64.dll` (тулчейн на Linux-хосте есть,
сабмодули FEX пустые, сборка не проверялась). Риски:
- поколения буфера на iOS и миграция потоков между буферами — таблица строго на буфер;
- исходящие связи переиспользованного блока могут указывать в уже стёртые блоки — `Erase` их
  отвязывает (переход через диспетчер), это безопасно, но проверить на мультиблоках;
- конкурентные потоки: публикация из боковой таблицы должна идти под теми же замками, что и
  компиляция (`CodeInvalidationMutex` shared + запись карты);
- iOS-особенности ловушки (ml657/ml1018/fast-path) не меняются, но точная инвалидация оставляет
  страницу под ловушкой → больше ловушек на одну страницу, если anti-tamper пишет в неё много раз за цикл
  (сейчас вторая и далее записи бесплатны);
- если слот — данные внутри `.text`, а не код, то k = 0 и хватит одной точной инвалидации.

## 4. Альтернативы и сравнение

**Режимы `SMCChecks` FEX** [факт по коду]: `none` / `mtrack` (по умолчанию, защита страниц) / `full`
(«Validate code before every run (slow)» — `ValidateCode` перед **каждой** гостевой инструкцией каждого
блока, Core.cpp:1018, BranchOps.cpp:574: загрузка + константа + сравнение на каждые 4–8 байт кода).
На Windows-фронтенде ловушки страниц отключаются **только** при `none`
(`InvalidationTracker.cpp:60`), поэтому `full` = те же ловушки и инвалидации **плюс** проверка везде —
строго дороже. `none` — anti-tamper исполнит устаревшую трансляцию (падение/срабатывание защиты) [версия,
высокая уверенность]. Режима «не защищать страницы, а сверять на входе в блок» в FEX нет; нужен код.

**«Горячие слоты» (anti-tamper-специфично)** — по образцу Mono-бэкпатчера, который в этом же FEX уже есть
(`DetectMonoBackpatcherBlock`, `MarkMonoBackpatcherBlock`, флаг `ForceFullSMCDetection` у блока):
- после N ловушек на один и тот же `[ea, ea+4)` записать его в список слотов (их ~33, список
  стабилен между прогонами — можно даже задать заранее для DS3);
- блоки, накрывающие слот, компилировать с `ForceFullSMCDetection` (проверка только этих байт на
  входе, единицы инструкций);
- ловушка, целиком попавшая в слот: выполнить запись через RW-алиас и **ничего не инвалидировать**,
  страницу оставить под ловушкой. Изменившийся код ловит проверка в блоке → `ThreadRemoveCodeEntry` →
  перекомпиляция одного блока (а с кэшем из §3 — повторное использование).

| Вариант | Компиляции от SMC | Сброс call-ret, NtProtect | Ловушки | Цена работ | Зависит от цикла |
|---|---|---|---|---|---|
| Сейчас | ~1 000+/с | ~500/с, ~240/с | 240/с | — | — |
| Пропуск одинаковых (b8a21b3) | −0.1…7 % | то же | −0.1…7 % | готово, не собрано | — |
| `SMCChecks=full` | то же | то же | то же | 0 | хуже везде |
| Точная инвалидация | → k на ловушку | остаются | 240/с+ | средняя, пересборка DLL | нет |
| Кэш по содержимому | → 0 / k | остаются | 240/с | 300–500 строк, пересборка DLL | да |
| Горячие слоты | → 0 (при цикле) / 1 на запись (без) | **→ 0** | 240/с (каждая запись в слот, но дешёвая) | ~150–250 строк, пересборка DLL, есть образец Mono | частично |

Рекомендация [оценка]: сначала одним прогоном снять `[smc-cyc]` (§1.3) — он решает, нужен ли кэш вообще.
Дальше — «горячие слоты» (наибольший выигрыш за наименьший код, без сбросов call-ret), кэш по содержимому
— вторым шагом, если `old_rep` высок, а слотов окажется больше, чем удобно перечислять.
