# DS3: программный TSO в FEX — сколько стоит и что можно снять

Дата: 20.10.2026. FEX: `<build-tree>/fex-build/FEX`, HEAD `a88141ba0` (exp/hot-smc-v2; от `f59cab9` отличается только hot-SMC, TSO-код идентичен — проверено `git diff`).
Пометки: **[факт]** — прочитано в коде / посчитано из лога или exe; **[оценка]** — арифметика на фактах; **[версия]** — не измерено.
Дополняет `DS3-HW-TSO.md` (аппаратный TSO недоступен) и исправляет пункт 13 в `DS3-PERF-knobs.md`.

## 1. Как этот FEX эмулирует TSO

Эффективная конфигурация (лог 22:17, строка `FEX: TSO config tso=true halfbar=true vector=false memcpyset=false`) и
`ml1231 iOS ARM64EC host features: LRCPC2=true` **[факт]**.

| Доступ гостя | Во что превращается | Где в коде |
|---|---|---|
| GPR load (`mov reg,[mem]`, `add reg,[mem]`, `cmp [mem],imm` …) | `LDAPUR` (смещение −256..255) или `ADD`+`LDAPR`; **+1 `NOP`** под бэкпатч | JIT/MemoryOps.cpp `DEF_OP(LoadMemTSO)`; Addressing.cpp:98 |
| GPR store | `NOP` + `STLUR` / `ADD`+`STLR` (+`NOP`) | MemoryOps.cpp `DEF_OP(StoreMemTSO)` |
| То же, база **RSP** | обычный `LDR/STR` | OpcodeDispatcher.h:1526 `IsNonTSOReg` — только RSP, **RBP не освобождён** |
| push/pop/call/ret | обычные | — |
| SSE/x87 (FPR) | обычный `LDR/STR`, без DMB (`VectorTSOEnabled=false`) | OpcodeDispatcher.h:2457 |
| `rep movs/stos` | неупорядоченный memcpy (`MemcpySetTSOEnabled=false`) | OpcodeDispatcher.cpp:3224–3296 |
| `lock`-инструкции | атомики LSE с acq/rel — всегда, от TSO не зависят | — |
| Невыровненный упорядоченный доступ | ловится SIGBUS → бэкпатч в «полубарьер» `DMB`+обычный доступ (`HalfBarrierTSOEnabled=true`) | TSOHandlerConfig.h |

Скрытые потери кроме самого порядка **[факт по коду]**: у упорядоченных GPR-доступов нет пар `LDP/STP` (OpcodeDispatcher.h `_LoadMemPairAutoTSO`), нет режима `[base+index*scale]` и смещений >255 (лишний `ADD`), плюс `NOP` на каждый.
`StrictInProcessSplitLocks=false`, `ParanoidTSO` в этом дереве **нет** **[факт]**. Никаких «TSO только после второго потока / по потокам / авто-миграции» тоже нет — TSO решается один раз на весь процесс (`Context.h UpdateAtomicTSOEmulationConfig`) **[факт]**.

**Доля упорядоченных операций в коде DS3** — статическая выборка 4×256 КБ из `.text` (capstone, 274 тыс. инструкций) **[факт]**:
- явных обращений к памяти 98.7 тыс.; из них SSE/x87 17.4 тыс. (без порядка), через RSP 16.0 тыс. (без порядка);
- **упорядоченных GPR-доступов 65.2 тыс. = 66 % обращений к памяти = ~24 % всех инструкций** (из них через RBP 8.3 тыс., RIP-глобалы 2.9 тыс.).
- Динамическая доля в горячем коде **не измерена** (нет семплера гостевых RIP) — [версия]: того же порядка, 20–25 % инструкций.

## 2. Варианты

### a) `FEX_TSOENABLED=0` глобально
Все GPR-доступы становятся обычными. Ломается то, что опирается на порядок x86 без `lock`: публикация через обычную запись флага/указателя после данных (lock-free очереди, «готово»-флаги, отпускание спинлока `mov [lock],0`), double-checked init. У DS3 это FD4JobWorker-очередь, команды GXWorker → GXRenderThread, звук, стриминг. Типичные симптомы [версия]: редкие вылеты на мусорном указателе, зависание на ожидании, мигание/битые меши, щелчки звука; порча сейва маловероятна, но возможна. Критические секции (Windows `CriticalSection`/SRW) сами по себе остаются корректными — они на `lock`-атомиках.

### b) По модулям / диапазонам: `FEX_EXTENDEDVOLATILEMETADATA`
- **Синтаксис** (Config.json.in:583, VolatileMetadata.cpp): `модуль[;начало-конец,...[;адрес,...]][:модуль2...]`, числа — hex-смещения от базы модуля; модуль сравнивается с именем файла как есть (`DarkSoulsIII.exe`). В Madeira — строка `env.FEX_EXTENDEDVOLATILEMETADATA = …` в madeira.cfg или в «This game's config» (FEX читает `FEX_*` из окружения; `;` парсер madeira.cfg не трогает) **[факт]**.
- **Смысл** (как у MSVC `/volatileMetadata`): «диапазон» = здесь метаданные **действительны**, т.е. TSO можно снять; «адреса» = инструкции, которым TSO **оставить**. Обратной формы «включить TSO только здесь» нет.
- **В самом exe метаданных нет**: `DarkSoulsIII.exe` собран линкером 11.0 (VS2012), каталога LoadConfig нет вовсе **[факт, pefile]**. Метаданные есть только у Steam-DLL (лог: steamclient64 5343, video64 1246, gameoverlayrenderer64 465, tier0_s64 336 записей) **[факт]**.
- **⚠️ Главная находка — в этом дереве форма «только модуль» и «модуль;диапазон» для DS3 ничего не делает** **[факт по коду, на устройстве не проверено]**. `Core.cpp:957–961`: блок получает «TSO снят» только если в нём есть **хотя бы один адрес из списка инструкций**; иначе — обычный TSO. Список общий на процесс; для кода exe (0x14…) `lower_bound` отдаёт первую запись steamclient64 (0x71F9…), она > конца блока → без изменений. Если список пуст — разыменование `end()` (неопределённое поведение; в апстриме позже добавили проверку `It != end()`, но логика «нет адреса → TSO включён» осталась и там — пример из блога FEX-2510 `iw4sp.exe;0xe9da0-0xe9ec7` на текущем апстриме, по коду, тоже не сработает). Значит пункт 13 в `DS3-PERF-knobs.md` («`= <dll>` снимает TSO в модуле») для этой сборки неверен.
- Обход без пересборки: в третьей секции перечислить адрес **внутри каждой** инструкции диапазона, но не её начало (например, `начало+1`) — тогда каждый блок «помечен», а ни одна инструкция TSO не получает. Работает только для небольших горячих функций (сотни адресов).

### c) Снять TSO только с однопоточного кода
Механизм есть — это (b) с диапазонами. Безопасно, если в диапазоне **нет ни одного** обычного (без `lock`) чтения/записи, через которое потоки передают друг другу данные: работа по стеку через RBP/другие регистры, TLS, буферы, принадлежащие одному потоку, математика/анимация/скиннинг над своим массивом. Опасно: код, читающий флаг/счётчик, выставленный другим потоком, и всё, что пишет в общие очереди. Нужен список горячих функций (семплер гостевых RIP) и ручная проверка каждой — **сейчас такого списка нет**.

## 3. Выигрыш

- FEX: эмуляция модели памяти — «главный тормоз»; «почти 10× даже с LRCPC/LRCPC2» — про векторный TSO (https://fex-emu.com/FEX-2404/), он у нас уже выключен. Векторный и memcpy TSO по умолчанию выключены с FEX-2406 как «слишком дорогие». Отдельных цифр для «только GPR + LRCPC2» FEX не публикует **[факт: в просмотренных постах 2306–2602 (выборочно, grep по «TSO») их нет]**.
- Для DS3 [оценка]: ~24 % инструкций упорядочены; на Apple-ядрах `LDAPR` дёшев, дороги `STLR`/`STLUR` и потеря `LDP/STP` + лишние `ADD/NOP`. [версия] **10–25 % времени главного потока** при полном снятии; для цели 30 fps нужно ~35 % — **одним TSO цель не достигается**. Плюс помнить: по `DS3-PERF-next.md` главный поток занят 62–64 %, кадр ограничен цепочкой ожиданий и GPU (сцена B: потолок GPU ≈31 fps).
- (b)/(c) дают долю от (a), пропорционально тому, сколько горячего времени покрыто диапазонами.

## 4. Минимальный безопасный эксперимент (без пересборки)

Цель — **узнать потолок** выигрыша, а не играть так. Бэкап сейва (`%APPDATA%\DarkSoulsIII\…\DS30000.sl2`) до запуска.
```
env.FEX_TSOENABLED = 0
```
(в «This game's config» для DS3, а не в общем madeira.cfg). Проверка, что применилось: в логе строка `TSO config tso=false`. Замер: та же сцена B 3–5 мин, сравнить `[gpu-perf]` FPS и `[xp-t]` главного потока (мс и млн инструкций на окно) с прогоном 20:03. Вернуть строку сразу после замера.
Если выигрыш < 10 % — направление закрыть. Если ≥ 20 % — имеет смысл патч ниже.

## 5. Патч FEX, если потолок окажется высоким (сборка `build-xtajit.sh`)

1. **Починить семантику диапазонов** (`FEXCore/Source/Interface/Core/Core.cpp:957`): если блок целиком в действительном диапазоне — `BlockInForceTSOValidRange = true` всегда, а `InstForceTSOIt = (It != end && *It < конец блока) ? It : end`. Тогда `DarkSoulsIII.exe;a-b` реально снимает TSO в диапазоне, а модуль целиком — по всему exe. ~5 строк.
2. Счётчик в лог: сколько блоков/инструкций скомпилировано с `ForceDisabled` — чтобы видеть, что строка в конфиге сработала.
3. Для (c) — семплер гостевых RIP главного потока (раз в N мс в обработчике `[xp-t]`), чтобы получить список горячих функций и снимать TSO точечно, с ручной проверкой каждой.
Риск патча 1 для других игр: модули со своими метаданными MSVC (Steam-DLL) начнут получать снятие TSO во всех блоках диапазона, а не только в блоках с volatile-доступами — это и есть задуманная MSVC семантика, но поведение изменится.
